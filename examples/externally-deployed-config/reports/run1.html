Indicator & score philosophy — read before treating any of this as a grade

The four indicators above separate two different questions this skill used to blend into one number: whether the docs are accurate (Documentation fidelity) is a different axis from whether the architecture is sound (Architecture risk) — a repo can improve one and regress the other. Audit coverage says how much of the mandatory checklist actually got run (not how many problems were found); Evidence confidence says how much of what's reported rests on direct citation versus inference. A dash (—) means that indicator legitimately wasn't computed for this run (wrong mode, or an older report predating that field) — never a fabricated zero.

Debt index (secondary, 0-100) is the original heuristic, debt-weighted signal, kept for continuity with earlier reports. Only risk, misaligned, and gap findings count against it, weighted by severity (high=6, medium=3, low=1, info=0) and summed per dimension, each dimension capped at 15, before those capped totals are added together; strength findings give a small capped bonus (+1 each, max +5). Deeper review surfaces more findings, so it isn't comparable across repos or across runs at different scope/depth — use it to track one repo's trend, not to rank systems against each other. Findings aren't independent (several may share one root cause and still get penalized separately). It reflects severity as judged during this review, not business impact or likelihood.

Key pressing findings
  • Risk High DeliverySender's outbound call to a subscriber's target_url has no timeout, retry budget, or circuit breaker configured, unlike the structurally similar SubscriptionRegistryClient call in the same codebase
  • Risk High Neither of this service's two critical logic paths — event ingestion (DomainEventConsumer) or delivery retry (DeliveryRetryJob) — emits any of the four golden signals (traffic, errors, latency, saturation)
  • Risk High DeliveryRetryJob — the code path responsible for recovering from delivery failures — produces no output of any kind (not a metric, not even a log line) describing its outcome
  • Risk High DeliveryRetryJob resends the identical payload to a subscriber on every retry with no idempotency key or header, so a subscriber that already processed a request but whose acknowledgment was lost will receive and potentially reprocess a duplicate
  • Risk High DeliverySender.attempt has no per-call timeout or circuit breaker, so a single hanging subscriber can stall the entire single-threaded DeliveryRetryJob run, delaying every other pending delivery in that batch
  • Risk High The domain-events consumer has no dead-letter topic and no failure-strategy override, meaning an unhandled exception in onEvent() (e.g. a persistence failure) would be handled by the messaging connector's default failure strategy, which can halt the channel rather than skip the one bad message
  • Risk High DeliverySender posts to target_url exactly as resolved from SubscriptionRegistryClient with no validation of scheme or host, so a compromised or misconfigured subscription-registry entry could direct this service to make requests to internal infrastructure
  • Misaligned Medium There is exactly one write path per delivery attempt — no code path writes to webhook_delivery and a second system in the same operation, so reliability-resilience.d (transaction-boundary correctness across dual writes) is legitimately not-applicable here, not a gap

Misaligned
Reliability / Resilience · Medium
confidence: medium
There is exactly one write path per delivery attempt — no code path writes to webhook_delivery and a second system in the same operation, so reliability-resilience.d (transaction-boundary correctness across dual writes) is legitimately not-applicable here, not a gap
The doc's 'no dual-write' claim defines 'write' narrowly as a second database/system being written to — but the outbound HTTP POST to the subscriber is itself an external side effect that occurs before the local transaction commits. If the POST succeeds (the subscriber received and processed the event) and the transaction subsequently fails to commit (crash, connection loss) before markDelivered()/scheduleRetry() persist, the row remains PENDING and the next retry cycle re-POSTs the identical payload — a duplicate delivery to the subscriber. This is the same class of hazard 'dual-write' correctness checks exist to catch, just external-side-effect-plus-local-commit rather than DB-to-DB; the doc's blanket not-applicable claim doesn't hold once the outbound call is counted as the 'write' it functionally is.
Recommendation: Either reframe technical-vision.md's claim to scope it explicitly to DB-to-DB dual writes (so it stops implying the retry path has no partial-failure exposure at all), or close the actual gap: send an idempotency key/header on each delivery attempt so a subscriber can safely dedupe a retried POST that was already processed.

Scalability · Medium
confidence: high
DeliveryRetryJob's BATCH_SIZE=200 is a hardcoded, undocumented cap on how many due deliveries are retried per interval, with no environment override
This caps recovery throughput at 200 rows per interval (default 1 minute). Combined with the uncapped-retry gap (f18/f41), a backlog of permanently-failing rows would consume retry slots forever and could eventually push legitimate still-recoverable deliveries out past the batch window, silently slowing recovery for everyone else — a second-order consequence of the retry-ceiling gap that's easy to miss looking at either issue alone.
Recommendation: Make BATCH_SIZE configurable, and prioritize the retry query so freshly-failing deliveries aren't starved behind a growing pool of forever-retrying ones once the retry-ceiling gap is fixed.

Risk
Security Boundaries · High
confidence: medium
DeliverySender posts to target_url exactly as resolved from SubscriptionRegistryClient with no validation of scheme or host, so a compromised or misconfigured subscription-registry entry could direct this service to make requests to internal infrastructure
target_url crosses a real trust boundary: it originates from a separate service (subscription-registry) and is trusted implicitly by DeliverySender, which will POST the domain event's payload to whatever URL that service returns. If subscription-registry is ever compromised, misconfigured, or has a validation gap of its own that lets a subscriber register an internal-network URL, this service becomes a vector for making authenticated-looking outbound requests to internal infrastructure (an SSRF-shaped risk) — and per f34, such a request would produce no operator-visible signal either way.
Recommendation: Validate target_url before use (https-only, reject private/loopback/link-local IP ranges and cloud metadata addresses) either in this service or, more centrally, at write-time in subscription-registry, and treat this as a cross-service trust-boundary decision that needs to be made explicitly rather than left implicit.
